## Added

- ZIP 234 halving-preserving reissuance, as drafted in
  [zcash/zips#1354](https://github.com/zcash/zips/pull/1354), behind the
  off-by-default `nu7` build feature. Each block adds
  `ceil(4126 / 10^10 * IssuanceDeficit)` to the halving subsidy, where the
  deficit is the scheduled supply minus the issued supply after the parent
  block. At 25-second blocks the deficit halves about every 1.33 years
  ([#859](https://github.com/zakura-core/zakura/pull/859)).
- Reissuance starts at a height that no ZIP defines. zips#1354 starts it at NU7
  activation, but the 2026-09-14 coinholder poll chose February 2031. Zakura
  applies ZIP 234's own start definition after the third halving instead of
  the second: the start is the lowest height after the third halving at which
  `ceil(4126 / 10^10 * (MAX_MONEY - scheduled supply))` is less than the
  halving subsidy, on the 75-second schedule, with the reserve following the
  scheduled supply. On Mainnet this is height 5,342,746, about 2031-02-14.
  ZIP 218's 25-second blocks map that height to the real chain through the
  halving clock, and reissuance never starts before NU7
  ([#859](https://github.com/zakura-core/zakura/pull/859)).
- Configured testnets and Regtest can set the reissuance start height with
  `testnet_parameters.zip234_start_height`. Mainnet and the default Testnet
  always use the crossing rule
  ([#859](https://github.com/zakura-core/zakura/pull/859)).
- Contextual validation rejects a block at or after the reissuance start height
  whose chain value pools make the issued supply exceed the expected issued
  supply, because zips#1354 forbids a negative issuance deficit. Both the
  non-finalized and the finalized commit paths return
  `ValidateContextError::NegativeIssuanceDeficit`
  ([#859](https://github.com/zakura-core/zakura/pull/859)).
- The block subsidy calculation returns `SubsidyError::NegativeIssuanceDeficit`
  if the deficit after the parent block is negative. Only the parent of the
  start height, which contextual validation does not check, or a money reserve
  from outside the chain state can reach it. `getblocktemplate` and
  `getblocksubsidy` return it as an RPC error
  ([#859](https://github.com/zakura-core/zakura/pull/859)).
- `subsidy::expected_issued_supply` and `ValueBalance::issued_supply` return
  zips#1354's `ExpectedIssuedSupply` and the protocol's `IssuedSupply`
  ([#859](https://github.com/zakura-core/zakura/pull/859)).

## Changed

- `block_subsidy` takes the money reserve after the parent block, which ZIP 234
  needs. A caller that reaches a ZIP 234 height without the money reserve gets a
  `MissingMoneyReserve` error rather than a wrong subsidy. The block info
  database upgrade supplies the reserve from its running value pools, and fails
  on an invalid subsidy
  ([#859](https://github.com/zakura-core/zakura/pull/859)).
- `select_mempool_transactions` returns an error instead of panicking when it
  cannot build the coinbase transaction
  ([#859](https://github.com/zakura-core/zakura/pull/859)).
- `ReadRequest::BlockInfo` searches every non-finalized chain instead of only the
  best chain, so a block verifier can look up a parent on a fork. Height queries
  still resolve on the best chain first
  ([#859](https://github.com/zakura-core/zakura/pull/859)).
- `Request::AwaitBlockInfo` waits for a block to commit before it returns the
  block's chain value pools. ZIP 234 verification uses this request for parent
  blocks that are still being verified
  ([#859](https://github.com/zakura-core/zakura/pull/859)).
