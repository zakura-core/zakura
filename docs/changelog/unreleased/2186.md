## Added

- A chain can now be configured to validate post-quantum transparent outputs, which name
  their format and signature scheme in the output and commit to the script a spend executes.
  A node applying these rules refuses a payment to an output nothing can spend, in the
  transaction that creates it, and refuses to run such an output under the legacy rules,
  which would otherwise hand it to anyone. A script of that shape revealed as a
  pay-to-script-hash redeem script keeps the legacy rules, so no existing output can be
  frozen; it is not post-quantum protected there. Spends, mixed transactions,
  signature-operation accounting, relay policy and mining are all covered. The setting,
  `network.params.pq_activation_height`, stands in for the network upgrade that will carry
  these rules, and is accepted only for Regtest and only on a build with the `pq` feature;
  the public networks are unchanged
  ([#2186](https://github.com/zakura-core/zakura/pull/2186)).
- Until the post-quantum rules apply, a payment to a script of their shape, or a spend of
  one, is non-standard by name. The legacy rules let anyone spend such a script with an
  empty scriptSig, and it was non-standard before only because no template matched it
  ([#2186](https://github.com/zakura-core/zakura/pull/2186)).

## Changed

- A unified address carrying a post-quantum receiver is accepted rather than rejected. The
  node keeps no destination for one, never mines to it, and leaves it out of
  `z_listunifiedreceivers`, which has no address string to report for it yet
  ([#2186](https://github.com/zakura-core/zakura/pull/2186)).
