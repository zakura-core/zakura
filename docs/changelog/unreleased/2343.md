## Changed

- `getblocktemplate` now answers a long poll on a new tip with the full
  template when the mempool already holds transactions for that tip, instead
  of always answering with a coinbase-only template first. It still answers
  coinbase-only when the mempool is empty, has not processed the new block
  within 10 ms, the miner address is shielded and its coinbase was built in
  advance, or three other long polls are already building a full template for
  a new tip ([#2343](https://github.com/zakura-core/zakura/pull/2343)).
- `getblocktemplate` builds a template for a miner paid to a transparent
  address without handing the build to another thread, which removes a wait
  that was longer than the build itself when a new block arrives. Templates
  that need a proof for a shielded miner reward are built as before, and
  templates are still built one at a time
  ([#2343](https://github.com/zakura-core/zakura/pull/2343)).
- `getblocktemplate` long polls that ask for the same work now share one
  template: the first builds it and the others take it, instead of each
  choosing transactions and building its own. Miners sharing a template get
  the same transactions and work ID. Requests without a long poll ID still
  get a template of their own
  ([#2343](https://github.com/zakura-core/zakura/pull/2343)).
- Reusing a shared template renews or restores its work-ID registration so
  compact submissions can reconstruct work after cache expiry or eviction.
  A shared template that has not been validated yet is queued for validation
  each time it is given out, as every template was before, and is validated
  once however often it is given out
  ([#2343](https://github.com/zakura-core/zakura/pull/2343)).
- A `getblocktemplate` long poll that is given a template other long polls
  already have no longer encodes the whole answer again: the answer's JSON
  is kept with the shared template and copied into the response. The bytes
  sent are unchanged
  ([#2343](https://github.com/zakura-core/zakura/pull/2343)).
- On a new tip the node now builds the `getblocktemplate` template without
  waiting for a request, so a request that arrives after the block is
  answered from it instead of building its own. A request without a long
  poll ID takes that template only when it is the one the node would build
  for it in that second; otherwise it builds its own, as before. The node
  starts doing this only after it is first asked for a template, so a node
  with a miner address that no miner uses does no extra work on each block
  ([#2343](https://github.com/zakura-core/zakura/pull/2343)).
- `getblocktemplate` no longer waits for the mempool on a new tip when the
  wait is not expected to pay off. The mempool now reports how much work a
  new block is before it removes that block's transactions, and keeps what it
  holds published as it changes. A long poll that wakes on a new tip
  estimates the block's work from what the mempool holds and the block's
  transaction count, and returns the coinbase-only template at once when the
  mempool holds nothing or the work is more than it is expected to finish
  within the wait, without waiting for the mempool's report or sending it a
  request. Otherwise it waits at most
  5 ms (was 10 ms), and answers coinbase-only if it only gets to run after
  that. The `mempool_tip_processed` trace rows record the reported work in its
  parts (`block_parts`, `mempool_parts`, `work`), `ready_us`, the time from
  that report until the block's transactions are published, and `drained`,
  the finished downloads stored in that time;
  `gbt_empty_returned` rows record why the answer was coinbase-only
  ([#2343](https://github.com/zakura-core/zakura/pull/2343)).

## Fixed

- Reduced transaction admission and backlog replenishment overhead for large mempools
  while retaining fresh mining transaction lists
  ([#2343](https://github.com/zakura-core/zakura/pull/2343)).
